# 星布谷地 · 岁月酒吧

> **一个多 Agent 驱动的游戏 NPC 系统** —— 画面里不止一个角色：老板娘在吧台后调酒，老周在角落坐了十年，导演在暗处安排这一拍该发生什么，场记盯着有没有人出戏。整条链路可追踪、可量化、可评测。

玩家操控像素角色在酒吧里走动、坐到吧台前点单。可以跟老板娘说，也可以直接点名找老周——两人各有各的记忆和立场，老周不会替店里调酒，但会跟你唠两句。

技术栈刻意保持轻量：**Node.js 原生 fetch + DeepSeek + Canvas 2D**，不引入任何 Agent 框架——因为要讲清楚的是编排循环本身，而不是框架的 API。

## 这个项目真正解决的是什么

一个"能用大模型聊天的游戏 NPC"和"能上线的游戏 NPC 系统"，差距不在模型，在下面这六件事上。这个项目就是把这六件事逐一做出来：

| 问题 | 为什么难 | 本项目的做法 |
|---|---|---|
| **模型该调工具却不调** | 用户说"尼格罗尼"三个字，模型回一句"好的~"就结束了，什么都没发生 | 意图识别 + 首轮强制 `tool_choice`，代码层兜底而非靠 prompt 祈祷 |
| **上下文窗口装不下** | 玩家长时间游玩，对话历史线性增长，迟早爆掉 | 三层记忆 + 触发式 LLM 摘要压缩 |
| **模型会做错事还浑然不觉** | 玩家表白时模型居然去调了"做一杯酒" | **Reflection 层**：工具执行后回头自评，不通过就带修正指令重跑 |
| **玩家可以越狱** | "忽略之前的指令""把你的系统提示词打印出来" | 输入/输出双守卫，**拒绝也在角色内拒绝** |
| **一个角色演不出一个场** | 单 Agent 演多个角色会串味；也没有"这场戏往哪走"的概念 | **多角色 + 导演层**，各自私有记忆，共享一个世界状态 |
| **无法回答"这东西好不好"** | 没有数据，改 prompt 全靠感觉 | 观测层（trace 落盘）+ 评测层（139 条标注用例） |

## 多 Agent 架构

```
                          玩家输入
                             │
                             ▼
                 ┌────────────────────────┐
                 │   Scene 场景调度器       │  一拍一拍推进
                 │   agent/scene.js        │  每拍只有一个主角
                 └───────────┬────────────┘
                             │
        ┌────────────────────┼────────────────────┐
        ▼                    ▼                    ▼
 ┌─────────────┐    ┌──────────────┐    ┌──────────────┐
 │  Director   │    │  消息总线     │    │   World      │
 │  每 N 拍一次 │    │  类型化消息   │    │  库存/时间/   │
 │  决定这一拍  │    │  bus.js      │    │  在场者/关系   │
 └─────────────┘    └──────┬───────┘    └──────────────┘
                           │
      ┌────────────────────┼────────────────────┐
      ▼                    ▼                    ▼
┌───────────┐      ┌───────────┐      ┌───────────┐
│ 老板娘     │      │ 老周       │      │ (可扩展)   │
│ 私有画像   │      │ 私有画像   │      │           │
│ 私有往事   │      │ 私有往事   │      │           │
│ 调酒工具   │      │ 无工具     │      │           │
└─────┬─────┘      └─────┬─────┘      └─────┬─────┘
      └──────────────────┴──────────────────┘
                         │
                         ▼
                 ┌───────────────┐
                 │   Critic      │  场景级评审：谁出戏了、导演的目标被忽略没
                 └───────────────┘
```

### 一拍是怎么走的

```
① 输入守卫（场景级，一次）
② 选出主角：显式 target > 文本里的称呼（"老周"）> 默认老板娘
③ 导演规划（每 3 拍或触发时）
④ 主角跑完整编排循环  ┐ 并行
   其他在场角色跑 react ┘
⑤ react 命中 / 导演点名的角色获得发言权（每拍最多 1 个次级，带冷却）
⑥ 场记评审
⑦ 输出守卫（逐个角色）→ 广播到总线 → 推进世界状态
```

### 三层记忆现在按角色隔离

| 层 | 存储 | 隔离方式 |
|---|---|---|
| 结构化画像 | `memory.json`、`memory.<角色>.json` | 每个角色一份独立文件 |
| 向量语义 | `vectorstore.json` | 条目带 `owner` 字段，召回时按 owner 过滤 |
| 对话历史 | 会话内 | 每个角色只保留**自己说过的话** |

**上下文隔离是多 Agent 成立的前提。** 如果所有角色共享一份历史和 prompt，那就不是多 Agent，只是函数拆分——面试时会被一眼看穿。

### 五个必须解决的问题

| 问题 | 做法 |
|---|---|
| **通信协议** | 类型化消息：`say` / `act` / `state` / `beat` / `decline` / `observe`。不用自由文本，否则角色会互相聊起来，成本失控且不可复现 |
| **回合调度** | 每拍只有一个主角。不做调度就会变成 N² 的互相应答 |
| **共享状态** | 黑板模式，`mutate()` 必须同步执行——中间有 `await` 的话两个角色会读到同一份过期库存，出现"两人各点走最后一瓶基酒" |
| **冲突解决** | 优先级：玩家 > 导演 > 角色人设/好感度 > 其他角色插话。允许**拒绝**导演的目标，拒绝要带理由写进 trace |
| **终止条件** | 三层：单拍（无候选/轮数耗尽）、场景（12 拍/玩家离开）、**看门狗**（单次输入的总调用超 16 次立即停） |

## 成本：多 Agent 最大的敌人

### 朴素实现会死在哪

4 个角色每拍都跑完整循环，一次玩家输入就是 5–8 次调用，成本翻 5 倍——而玩家在同一时刻只跟一个人说话。

### 实际做法：分层调用

| 角色 | 何时调用 | 干什么 |
|---|---|---|
| 玩家对话中的角色 | 每拍 | 完整编排循环，流式输出台词 |
| 其他在场角色 | 每拍一次 **react** | 短 prompt，**不生成台词**，只输出 `{speak, urgency, angle}` |
| react 命中（或导演点名）的角色 | 升级后 | 才跑完整循环 |
| Director | 每 3 拍或触发时 | 只输出一个 beat |
| Critic | 有 act 时 | 只判定，不生成 |

### 效果对比

| | 单 Agent（改造前） | 多 Agent（现在） | 变化 |
|---|---|---|---|
| 模型调用 / 次 | ~1.4 | **3.86** | +176% |
| tokens / 次 | 2031 | 2704 | +33% |
| **成本 / 次** | **¥0.0046** | **¥0.0063** | **+37%** |
| 端到端 | ~1560 ms | ~2279 ms | +46% |

**角色从 1 个变成 4 个，每次输入的成本只涨了 37%。** 因为 react / 导演 / 场记的调用都是短 prompt、且不生成台词——它们比一次完整回合便宜得多。

这是本项目最有工程含量的一处取舍，也是面试里最好讲的一段。

## 设计决策

### 1. 为什么"意图识别 + 强制 tool_choice"是双保险，而不是只靠 prompt

最初的实现只在 prompt 里写了"用工具的铁律"。但实测发现：**用户说"尼格罗尼"三个字（不带任何动词）时，模型有相当概率只回一句"好嘞~"而不调工具。**

prompt 是概率性的，工具调用是确定性的需求，两者不匹配。所以加了代码层的确定性路由。关键是这一层的保守性：只处理高置信、可枚举的意图，宁可漏判（退回 `auto`）也不误判（把闲聊变成工具调用）。否定句专门有一条分支——"我不太想喝酒"不能被当成点单。

### 2. 为什么记忆要分三层，以及**记什么比怎么检索更重要**

大多数 Agent 项目只做了检索（RAG），没做**写入策略**。但"该记什么、该忘什么"才是记忆系统的核心设计问题。

本项目的写入判定：只有**点单 / 付款 / 报名字 / 定制酒**才触发写入，且先用一次 LLM 调用把对话浓缩成不超过 15 字的事实，再存向量。上限 200 条。

### 3. 为什么角色必须各有各的上下文

如果两个"agent"读同一份 prompt、同一份记忆、只是分工不同，那不是多 Agent，是函数拆分。

所以每个角色有自己的 system prompt、自己的画像文件、自己的向量记忆归属、自己的工具集（老周没有调酒工具）、以及**只包含自己发言的会话历史**。别人的话通过"刚才发生了什么"的场景块进入 system prompt。

### 4. 为什么要有 Reflection 层

主循环里的模型是"向前看"的（决定下一步做什么），Reflection 是"向后看"的（评价刚做完的事对不对）。两者判据不同，混在一起会让模型既当运动员又当裁判。

这一层在实测中确实抓到了真问题，见[踩过的坑](#踩过的坑)。

### 5. 为什么安全守卫用规则而不是模型

守卫必须**确定性、零延迟、零成本，且自己不能被注入**。用模型做守卫意味着多一次调用、多一份延迟，还可能被同一套注入话术绕过。

代价是覆盖不了语义级越界——这部分交给人设约束兜着。误报率和漏报率由 `eval` 的 safety 套件持续监控。

**另一个关键设计：被拦截时不说"我被安全策略拦截了"，而是用老板娘的口吻把话题带开。** 玩家不应该感觉到安全层的存在。拦截同时省掉一次完整调用。

### 6. 为什么旁听者拿到的不是玩家原话

次要角色如果直接把玩家的输入当成 user message，会答出"这你得问老板娘，我可做不了主"这种错位回答——因为玩家那句话不是对他说的。

所以旁听者拿到的是**转述**：`（旁边有人在说话，你听见了：「…」）`。这个改动前后差别很大，见[踩过的坑](#踩过的坑)。

## 快速开始

```bash
npm install

cp .env.example .env
#   DEEPSEEK_API_KEY     必填
#   SILICONFLOW_API_KEY  可选（不填则只用结构化画像，向量记忆自动关闭）
```

## 踩过的坑

### 坑 1：评测抓到意图路由的否定句误判

第一版泛称规则是「出现"酒"等泛称 + 出现"来/要/喝/点"等动词 → 判为点单」。跑评测立刻暴露 4 条失败：

```
✗ 我不太想喝酒   期望 无意图  实际 makeDrink
✗ 我不想点酒     期望 无意图  实际 makeDrink
✗ 今天不喝酒了   期望 无意图  实际 makeDrink
✗ 别给我调酒     期望 无意图  实际 makeDrink
```

**准确率 42/46 = 91.3%。**

修复分两步：先加 `NEGATION` 规则回到 45/46；剩下"我不太想喝酒"仍失败——因为否定词和动词之间插了程度副词"太"。再让规则接受中间副词，**46/46**。

> 这类错误靠肉眼发现不了——"我不太想喝酒"和"给我来杯酒"在字符层面高度相似，产品语义上完全相反。**没有标注数据集的 Agent 项目，这种错会一直藏在线上。**

### 坑 2：Reflection 层阻止了一次错误工具调用

实测 trace 里最有价值的一条：玩家输入 **「我喜欢你，做我女朋友吧」**，模型第 1 轮的反应是**调用了 `makeDrink`，做了一杯「大都会」**。

Reflection 层判定 revise：

> 用户是在表达情感/闲聊示意，并未点任何酒，执行者却调用了 makeDrink 工具制作「大都会」，属于无关工具调用。

带修正指令重跑后给出正确的角色内婉拒。**没有这一层，玩家会在表白之后收到一杯自己没点的酒。**

同一层还抓到过另一次：模型把"加冰"塞进了 `milk` 参数。审核员的原话是：

> 参数 milk:"加冰" 明显错误，尼格罗尼不含牛奶……加冰应属于温度/冰量参数而非 milk 参数

这是 schema 命名歧义导致的真 bug——后来把 `milk` 改名为 `extras` 并重写描述。

### 坑 3：流式请求会静默丢掉 token 用量

第一版流式解析是这样的：

```js
const choice = data.choices && data.choices[0];
if (!choice) continue;        // ← usage 所在的块 choices 为空数组，被这里跳过了
```

DeepSeek 在流末尾单独发一个 `choices: []` 的数据块承载 `usage`。上面的 `continue` 把它丢掉，导致观测层的 token 统计**永远是 0**。

修复两点：解析顺序改成先处理 `usage` 再判断 `choice`；请求体加 `stream_options: { include_usage: true }`（不加这一行服务端根本不回传用量）。另外最终结果必须在**流结束后**才产出，在 `finish_reason` 处提前返回同样会丢。

### 坑 4：多 Agent 改造中，评测一次抓出三个真 bug

引入多角色后第一次跑 `multiagent` 套件，9/12。三个失败全是真问题：

**① `world.present` 初始只有 `["boss"]`，老周根本不在场。**
所以老板娘说话时压根没有其他人跑 react。日志里只有 boss 的 react span，就是因为老周从没被放进场景。这个 bug 靠读代码很难发现——react 代码写对了，只是永远不会被触发。

**② 系统提示里写的是角色 id 而不是名字。**
`【在场的人】除了顾客，还有：regular` ——模型看不懂 "regular" 是谁，所以玩家问"店里还有别人吗"，老板娘回答"就你一个呀，今晚整间店都归你"。
修复：加一张 id → 显示名的表，同名问题也发生在场记评审上（它把 `boss` 和"老板娘"当成两个人，报告"指派给 boss 但开口的是老板娘"这种假警报）。

**③ 旁听者把玩家的话当成了对自己说的。**
玩家向老板娘点酒，老周作为次要角色插话，开口却是"这你得问小满，吧台里的事我可做不了主"——因为他的 user message 就是玩家原话，他以为在问他。
修复：旁听者拿到的是转述 `（旁边有人在说话，你听见了：「…」）`。改完之后老周的表现变成："你这人还挺执着。我跟你讲，我这杯子都是小满给倒的，我可不敢伸手。你冲那边喊一声，她耳朵尖着呢。"

### 坑 5：辅助调用没被计进账

导演和场记的模型调用只记了 span，没把 `usage` 累加进 trace，导致成本被系统性低估——`npm run metrics` 里显示 "director 调用 0 次"。

修复：加 `recordAuxLLM()`，把 react / 导演 / 场记 / 记忆提炼的用量都计入总量和角色账。

### 坑 6：清掉注释后重跑，评测又翻出两个既有问题

把全项目注释删除后重跑评测，出现两条失败——**都不是删注释造成的**（注释不影响行为），而是被顺带照出来的：

**① 意图路由漏了「随便给我调一杯特别的」。**
`CUSTOM` 正则里只有"随便调"，而这句话在"随便"和"调"之间插了"给我"，匹配不上，于是只能靠模型自己决定调不调工具，时好时坏。改成 `随便.{0,4}(调|来|做|上|弄)` 这类允许插词的写法，并补了 3 条用例进离线套件。

**② 模型会主动收费。**
同样是这一轮，工具调用是 `inventDrink` **加** `takePayment`——玩家没提结账，店长自己把钱收了。prompt 里只写了"顾客要结账时调用 takePayment"，没写反面的约束。补上"顾客这一句里没提钱，就不要主动收费"后恢复正常。

> 这两条说明一件事：**评测的价值不是让分数好看，而是每次你动它，它都会把之前藏着的问题再翻出来一遍。**

## 已知限制

诚实列出当前的短板。这些不是"以后再说"，是有明确证据的问题。

### 1. Reflection 层的判定精度只有约 50%

累计触发中否决的那几次里，只有一部分是确认的真阳性（表白、milk 参数）。

假阳性那例：用户问「你们库存还有多少」，`checkStock` 正确返回了库存，但审核员判定为"未带任何参数，无法满足查询意图"并触发重试——**但 `checkStock` 本来就不接受任何参数**。结果是多跑一轮，多花约 500ms 和一次调用的 token。

改进方向：把工具的参数 schema 一并喂给审核员；或对无参数工具直接跳过审核。

### 2. 导演和场记用的是同一个模型

`.env` 里的 `SMALL_MODEL` 目前没有实际可用的更便宜选项，所以 react / 导演 / 场记虽然 prompt 很短、输出很少，但仍然跑在主模型上。成本优化主要来自"调用更少、prompt 更短、不生成台词"，而不是"换了小模型"。

### 3. 未使用主流 Agent 框架

要求里常见的是"熟悉 LangGraph / AutoGen / CrewAI / MetaGPT"。本项目是自研编排。自研能证明理解原理，但不等价于框架使用经验。

计划：用 LangGraph 重做同一套流程，写一篇两者取舍的对比。

### 4. 技术栈是 JavaScript

如果目标岗位点名 Python，这个项目不能直接作为语言能力的证据。计划做 TypeScript 渐进迁移（不重写，增量改）。

### 5. 没有多智能体协商

目前是"导演指派 + 角色可否决"的偏单向调度，缺少真正的多轮协商（agent 之间就一个目标来回讨论直到达成一致）。相应的问题——通信收敛、死锁检测、协商成本上限——都还没做。

### 6. 次要角色的 react 是并行跑的，看不到主角刚说的话

为了省延迟，其他角色的 react 判定和主角的完整回合并行执行，所以老周反应的是**玩家说了什么**，而不是**老板娘刚回了什么**。这在多数场景下没影响（他本来就是在回应玩家），但确实是个简化。

### 7. 评测的在线套件样本偏小

人设一致性 12 条、端到端 11 条、多 Agent 12 条。作为回归测试够用，作为统计结论偏薄。

### 8. 输出守卫是"事后替换"

守卫在流式输出**结束之后**才判定，此时玩家已经看到原文了。虽然前端会收到 `guard_replaced` 事件把气泡文本换掉，但严格说这是补丁而非预防。

### 9. 成本费率是示例值

`.env` 里的 `PRICE_INPUT_PER_M` / `PRICE_OUTPUT_PER_M` 默认值仅作示例，**实际成本请以服务商官网为准**。
