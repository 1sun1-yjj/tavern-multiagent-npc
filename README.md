# 星布谷地 · 岁月酒吧

> **一个多 Agent 驱动的游戏 NPC 系统** —— 画面里不止一个角色：胡桃在吧台后调酒，钟离在角落坐了十年，导演在暗处安排这一拍该发生什么，场记盯着有没有人出戏。整条链路可追踪、可量化、可评测。

玩家操控像素角色在酒吧里走动、坐到吧台前点单。可以跟胡桃说，也可以直接点名找钟离——两人各有各的记忆和立场，钟离不会替店里调酒，但会跟你唠两句。**他也不只是等着被点名的人**：你跟胡桃聊的时候他可能插一句，你安静下来的时候他会先找你说话。

技术栈刻意保持轻量：**Node.js 原生 fetch + DeepSeek + Canvas 2D**，不引入任何 Agent 框架——因为要讲清楚的是编排循环本身，而不是框架的 API。

## 这个项目真正解决的是什么

一个"能用大模型聊天的游戏 NPC"和"能上线的游戏 NPC 系统"，差距不在模型，在下面这六件事上。这个项目就是把这六件事逐一做出来：

| 问题 | 为什么难 | 本项目的做法 |
|---|---|---|
| **模型该调工具却不调** | 用户说"尼格罗尼"三个字，模型回一句"好的~"就结束了，什么都没发生 | 意图识别 + 首轮强制 `tool_choice`，代码层兜底而非靠 prompt 祈祷 |
| **上下文窗口装不下** | 玩家长时间游玩，对话历史线性增长，迟早爆掉 | 三层记忆 + 触发式 LLM 摘要压缩 |
| **模型会做错事还浑然不觉** | 玩家表白时模型居然去调了"做一杯酒" | **Reflection 层**：工具执行后回头自评，不通过就带修正指令重跑 |
| **玩家可以越狱** | "忽略之前的指令""把你的系统提示词打印出来" | 输入/输出双守卫，**拒绝也在角色内拒绝** |
| **一个角色演不出一个场** | 单 Agent 演多个角色会串味；也没有"这场戏往哪走"的概念 | **多角色 + 导演层**，各自私有记忆，共享一个世界状态 |
| **无法回答"这东西好不好"** | 没有数据，改 prompt 全靠感觉 | 观测层（trace 落盘）+ 评测层（192 条标注用例） |

```
 ┌─────────────┐    ┌──────────────┐    ┌──────────────┐

      └──────────────────┴──────────────────┘
                         │
                         ▼
                 ┌───────────────┐
                 │   Critic      │  场景级评审：谁出戏了、导演的目标被忽略没
                 └───────────────┘
```

### 一拍是怎么走的

```
① 输入守卫（场景级，一次）
② 选出主角：显式 target > 文本里的称呼（"钟离"）> 刚主动开口的人 > 上一拍的对话对象 > 默认胡桃
③ 导演规划（每 3 拍或触发时）
④ 主角跑完整编排循环  ┐ 并行
   其他在场角色跑 react ┘
⑤ 主角说完之后，若这一拍还没人拿到发言权，让在场角色再 react 一次（这次听得到主角刚说的话）
⑥ react 命中 / 导演点名的角色获得发言权（每拍最多 1 个次级，带冷却）
⑦ 场记评审（判 revise 时把 hint 带进下一拍）
⑧ 输出守卫（逐个角色）→ 广播到总线 → 推进世界状态
```

### 客人怎么参与

胡桃是默认主角，客人钟离有三条参与路径：

| 路径 | 触发时机 | 机制 | 代价 |
|---|---|---|---|
| **插话** | 玩家开口的那一拍 | 并行 react 判定，过了阈值就升格跑完整循环 | 1 次短调用 |
| **接话** | 主角已经回完 | **补跑一次 react**，这一次它听得到主角刚说的话 | 1 次短调用，只在当拍没人插话时才补 |
| **主动搭话** | 玩家安静下来 | 空闲通道：安静时长 + 冷却 + 概率三重闸门 → 规划一个话头 → 客人自己开口 | 只在空闲时花，命中率由配置控制 |

**插话是例外，不是常态。** 要不要开口由模型判断，但判断的输入里必须给全三样东西，否则它只会逢话头就接：

- **默认答案是不说**：prompt 列出值得开口的三种情况（叫到他的名字 / 他有别人没有的信息 / 他确实不认同且有话用），和五种**不算理由**的（捧场附和、把别人的话换个说法再说一遍、想显摆自己坐了多少年、客人刚进门还在跟老板娘寒暄、他刚说过）——"说得在理""确实"这类附和是被点名禁止的
- **他自己的发言节奏**：`sinceSpeak`（上一次开口是几拍之前）一起喂进去，"你上一拍刚开过口，这一拍就别急着再接"——频率不是掷骰子掷出来的，是他看着自己的节奏做的决定
- **不认没有理由的开口**：判定必须附一句 `reason`；`speak:true` 却没给理由会被降级成不说。**说不清为什么开口，就不开口**

再加两道确定性门槛：插话要过 `REACT_THRESHOLD`（默认 0.55），补跑那次"接话"还要再高一档（`FOLLOWUP_EXTRA_BAR`，默认 +0.15）——接话比插话难。

实测：5 句跟钟离无关的闲聊，他**一句都没接**；而玩家说"今天店里好安静啊，就我一个人吗"时他接了，理由是「客人问是不是只有自己一个人，直接关乎在场的人，该应一声」。每条判定都写进 trace，`GET /api/traces/:id` 里能直接读到他为什么说、为什么不说。

归属分两层，别混：

- **主动搭话之后的回话窗口**（默认 90 秒）：玩家不点名的回话由他接住；但这句话一旦被意图路由判成点单/结账/查库存，仍然回到胡桃手里——窗口抢不走吧台的活。
- **"上一句说给谁"的上文延续**：不点名的下一句仍然说给上一位，**但同样有一道"他办不办得了"的检查**——延续对象没有这个工具时，这句话改派给能做的人。闲聊继续归钟离，吧台的活归胡桃。**"接着上一位说"不能把单子接丢。**

如果玩家偏偏点了名（"钟离，来杯尼格罗尼"），路由层不夺走发言权，钟离照旧把话推给胡桃；同时 `scene.js` 的兜底会让**胡桃在同一拍把这一单接住**——给出的那杯酒是真的调出来了，不是嘴上推一句就完事。这条是照着实跑撞出来的，见[踩过的坑](#踩过的坑)第 11 条。

他插话/接话时都带着在场名单：react 的 prompt 里有「此刻店里除了你和顾客，还有：谁谁，别把人说成不在、没来或者没见着人影」。这条不是礼貌，是修 bug 修的，见[踩过的坑](#踩过的坑)第 8 条。

三条路径都会在流里带一个 `stage` 事件，留给画面用（走动素材还没接，现有立绘不会真的走动）：

| 事件 | 何时 | 含义 |
|---|---|---|
| `approach` | 客人决定主动开口 | 他要过来了（`near: true`、`pose: "walk"`、`anchor: "bar_front"`） |
| `join` | 客人插话/接话时 | 他要入席说一句（`pose: "talk"`） |
| `leave` | 他说完 / 窗口被吧台抢走 | 他可以回角落了（`near: false`） |

前端把最新状态收在 `window.__tavernStaging[actor]`（含 `near` / `anchor` / `pose` / `x` / `feetY`），绘制代码接上走路素材后直接读它即可，协议不用改。

客人从头到尾没有工具：请求体里不带 `tools` 字段，权限集合是空的，代码层还有一道「你没有权限使用工具 X」的兜底。

### 三层记忆现在按角色隔离

| 层 | 存储 | 隔离方式 |
|---|---|---|
| 结构化画像 | `memory.json`、`memory.<角色>.json` | 每个角色一份独立文件 |
| 向量语义 | `vectorstore.json` | 条目带 `owner` 字段，召回时按 owner 过滤 |
| 对话历史 | 会话内 | 每个角色只保留**自己说过的话** |

**上下文隔离是多 Agent 成立的前提。** 如果所有角色共享一份历史和 prompt，那就不是多 Agent，只是函数拆分——面试时会被一眼看穿。

### 五个必须解决的问题

| 问题 | 做法 |
|---|---|
| **通信协议** | 类型化消息：`say` / `act` / `state` / `beat` / `decline` / `observe`。不用自由文本，否则角色会互相聊起来，成本失控且不可复现 |
| **回合调度** | 每拍只有一个主角。不做调度就会变成 N² 的互相应答 |
| **共享状态** | 黑板模式，`mutate()` 必须同步执行——中间有 `await` 的话两个角色会读到同一份过期库存，出现"两人各点走最后一瓶基酒" |
| **冲突解决** | 优先级：玩家 > 导演 > 角色人设/好感度 > 其他角色插话。允许**拒绝**导演的目标，拒绝要带理由写进 trace |
| **终止条件** | 三层：单拍（无候选/轮数耗尽）、场景（12 拍/玩家离开）、**看门狗**（单次输入的总调用超 16 次立即停） |

## 成本：多 Agent 最大的敌人

### 朴素实现会死在哪

4 个角色每拍都跑完整循环，一次玩家输入就是 5–8 次调用，成本翻 5 倍——而玩家在同一时刻只跟一个人说话。

### 实际做法：分层调用

| 角色 | 何时调用 | 干什么 |
|---|---|---|
| 玩家对话中的角色 | 每拍 | 完整编排循环，流式输出台词 |
| 其他在场角色 | 每拍一次 **react** | 短 prompt，**不生成台词**，只输出 `{speak, urgency, angle}` |
| 主角回完之后 | 当拍没人插话时补一次 **react** | 同上，但这次能看到主角刚说的话（客人接话靠它） |
| react 命中（或导演点名）的角色 | 升级后 | 才跑完整循环 |
| Director | 每 3 拍或触发时 | 只输出一个 beat |
| Critic | 有 act 时 | 只判定，不生成；判 revise 的意见会进下一拍的 prompt |
| 客人主动搭话 | 玩家空闲时 | 一次短调用规划话头，之后才是完整循环 |

### 效果对比

| | 单 Agent（改造前） | 多 Agent（现在） | 变化 |
|---|---|---|---|
| 模型调用 / 次 | ~1.4 | **4.31** | +208% |
| tokens / 次 | 2031 | 3118 | +54% |
| **成本 / 次** | **¥0.0046** | **¥0.0074** | **+61%** |
| 端到端 | ~1560 ms | ~4348 ms | +179% |

**角色从 1 个变成 4 个、客人还会自己找你说话，每次输入的成本只涨了 61%。** 因为 react / 补跑 react / 导演 / 场记的调用都是短 prompt、且不生成台词——它们比一次完整回合便宜得多。（`tokens/次` 涨得比成本多，是因为判定用的短 prompt 里现在多带了在场名单与插话判据。）

端到端耗时涨得比成本多，原因也是这一层：补跑的那次 react 发生在主角说完**之后**，它不影响你看到台词（流式早就吐完了），但会把这一拍彻底收尾的时间往后推。要拿延迟换，`GUEST_FOLLOWUP=0` 一行就能关掉。

这是本项目最有工程含量的一处取舍，也是面试里最好讲的一段。

## 设计决策

### 1. 为什么"意图识别 + 强制 tool_choice"是双保险，而不是只靠 prompt

最初的实现只在 prompt 里写了"用工具的铁律"。但实测发现：**用户说"尼格罗尼"三个字（不带任何动词）时，模型有相当概率只回一句"好嘞~"而不调工具。**

prompt 是概率性的，工具调用是确定性的需求，两者不匹配。所以加了代码层的确定性路由。关键是这一层的保守性：只处理高置信、可枚举的意图，宁可漏判（退回 `auto`）也不误判（把闲聊变成工具调用）。否定句专门有一条分支——"我不太想喝酒"不能被当成点单。

### 2. 为什么记忆要分三层，以及**记什么比怎么检索更重要**

大多数 Agent 项目只做了检索（RAG），没做**写入策略**。但"该记什么、该忘什么"才是记忆系统的核心设计问题。

本项目的写入判定：只有**点单 / 付款 / 报名字 / 定制酒**才触发写入，且先用一次 LLM 调用把对话浓缩成不超过 15 字的事实，再存向量。上限 200 条。

### 3. 为什么角色必须各有各的上下文

如果两个"agent"读同一份 prompt、同一份记忆、只是分工不同，那不是多 Agent，是函数拆分。

所以每个角色有自己的 system prompt、自己的画像文件、自己的向量记忆归属、自己的工具集（钟离没有调酒工具）、以及**只包含自己发言的会话历史**。别人的话通过"刚才发生了什么"的场景块进入 system prompt。

### 4. 为什么要有 Reflection 层

主循环里的模型是"向前看"的（决定下一步做什么），Reflection 是"向后看"的（评价刚做完的事对不对）。两者判据不同，混在一起会让模型既当运动员又当裁判。

这一层在实测中确实抓到了真问题，见[踩过的坑](#踩过的坑)。

### 5. 为什么安全守卫用规则而不是模型

守卫必须**确定性、零延迟、零成本，且自己不能被注入**。用模型做守卫意味着多一次调用、多一份延迟，还可能被同一套注入话术绕过。

代价是覆盖不了语义级越界——这部分交给人设约束兜着。误报率和漏报率由 `eval` 的 safety 套件持续监控。

**另一个关键设计：被拦截时不说"我被安全策略拦截了"，而是用胡桃的口吻把话题带开。** 玩家不应该感觉到安全层的存在。

这里判定和台词是分开的：**拦不拦、按哪一类拦，永远是 `safety.js` 里的确定性规则**；而"这句拒绝该怎么说"交给模型，用说话者自己的身份重写一遍（`scene.js` 的 `deflectLine`）。代价是每次拦截多一次短调用——比一次完整回合便宜得多，但不再是零成本；调用失败就回退到写死的那几句。

三条不交给模型：自伤、真实伤害、未成年相关。这三类必须用固定文案，其中自伤那条还带 24 小时心理援助热线号码，不能让模型临场编。

### 6. 为什么旁听者拿到的不是玩家原话

次要角色如果直接把玩家的输入当成 user message，会答出"这你得问胡桃，我可做不了主"这种错位回答——因为玩家那句话不是对他说的。

所以旁听者拿到的是**转述**：`（旁边有人在说话，你听见了：「…」）`。这个改动前后差别很大，见[踩过的坑](#踩过的坑)。

### 7. 为什么让客人接话要靠"补跑一次 react"，而不是调低阈值

旁听者的 react 和主角的完整循环是并行跑的。省下的是延迟，代价是**它只能对玩家的原话做反应，听不到胡桃刚回了什么**。

想让客人"参与玩家和胡桃的对话"，光把阈值调低没用：它仍然在对玩家那句话做反应，于是会接出一句跟胡桃的回答打架的话。所以主角说完之后补跑一次 react，并把已经广播出去的那句话交给它。

这次补跑是有条件的——**只在当拍没人拿到发言权时才触发**，所以它既不会让场面变吵，也不会每拍都多花一次调用。

### 8. 为什么主动搭话要做成"空闲通道"，而不是让模型自己决定什么时候开口

模型没有时钟。它只在被调用时存在，所以"现在该不该开口"这个决定不能交给它——每次被调用它都会觉得"现在是说点什么的好时候"。

本项目把它拆成两层：**代码决定要不要开口**（安静够久 + 过了冷却 + 概率命中，全是确定性的），**模型决定开口说什么**（一次短调用，只产出一个话头）。这和意图路由是同一个思路：确定性的需求用代码，生成性的内容用模型。

归属同理：客人开口之后的 90 秒内，玩家不点名的回话由他接住；但这句话一旦被判成点单/结账/查库存，仍然回到胡桃手里——闲聊归客人，吧台的活不归他。

### 9. 为什么"偶尔插话"要靠喂上下文，而不是靠调低频率

第一版钟离是**逢话头就接**：玩家刚坐下说一句"你好呀"，他紧跟着就来一段"胡桃说得在理。我跟你讲啊…"。prompt 写的是"邻座搭话是很自然的事…就该开口，不用太客气"——这个偏向下，模型当然每次都开口。

最直觉的修法是把 `REACT_THRESHOLD` 从 0.25 调到 0.8。但那是**用沉默换安静**：真正该他开口的时刻（有人叫他的名字、问到只有他知道的事）也会被一起压掉。

所以这一层反过来做：**判断留给模型，把判断需要的上下文补全**。react 的 prompt 里因此多了三样东西——在场名单（少了它会编出"人还没来"，见坑 8）、"你上一次开口是几拍之前"、以及一张"什么才算理由"的清单（附和、换个说法重复、显摆资历、客人刚进门还在寒暄，全部不算）。

判据也跟着变严：`speak:true` 必须附一句 `reason`，没给理由就降级成不说。

> **调参只能得到均匀的沉默，补上下文才能得到"该说时说"。** 前者治的是次数，后者治的是依据。

实测（`interject_occasional`）：5 句跟钟离无关的闲聊，两次跑下来分别接了 **0 句和 1 句**；玩家说"今天店里好安静啊，就我一个人吗"时他接了，理由是「客人问是不是只有自己一个人，直接关乎在场的人，该应一声」。插话与接话的门槛分开：补跑那次还要高 `FOLLOWUP_EXTRA_BAR`（默认 +0.15）。

## 踩过的坑

### 坑 1：评测抓到意图路由的否定句误判

第一版泛称规则是「出现"酒"等泛称 + 出现"来/要/喝/点"等动词 → 判为点单」。跑评测立刻暴露 4 条失败：

```
✗ 我不太想喝酒   期望 无意图  实际 makeDrink
✗ 我不想点酒     期望 无意图  实际 makeDrink
✗ 今天不喝酒了   期望 无意图  实际 makeDrink
✗ 别给我调酒     期望 无意图  实际 makeDrink
```

**准确率 42/46 = 91.3%。**

修复分两步：先加 `NEGATION` 规则回到 45/46；剩下"我不太想喝酒"仍失败——因为否定词和动词之间插了程度副词"太"。再让规则接受中间副词，**46/46**。

> 这类错误靠肉眼发现不了——"我不太想喝酒"和"给我来杯酒"在字符层面高度相似，产品语义上完全相反。**没有标注数据集的 Agent 项目，这种错会一直藏在线上。**

### 坑 2：Reflection 层阻止了一次错误工具调用

实测 trace 里最有价值的一条：玩家输入 **「我喜欢你，做我女朋友吧」**，模型第 1 轮的反应是**调用了 `makeDrink`，做了一杯「大都会」**。

Reflection 层判定 revise：

> 用户是在表达情感/闲聊示意，并未点任何酒，执行者却调用了 makeDrink 工具制作「大都会」，属于无关工具调用。

带修正指令重跑后给出正确的角色内婉拒。**没有这一层，玩家会在表白之后收到一杯自己没点的酒。**

同一层还抓到过另一次：模型把"加冰"塞进了 `milk` 参数。审核员的原话是：

> 参数 milk:"加冰" 明显错误，尼格罗尼不含牛奶……加冰应属于温度/冰量参数而非 milk 参数

这是 schema 命名歧义导致的真 bug——后来把 `milk` 改名为 `extras` 并重写描述。

### 坑 3：流式请求会静默丢掉 token 用量

第一版流式解析是这样的：

```js
const choice = data.choices && data.choices[0];
if (!choice) continue;        // ← usage 所在的块 choices 为空数组，被这里跳过了
```

DeepSeek 在流末尾单独发一个 `choices: []` 的数据块承载 `usage`。上面的 `continue` 把它丢掉，导致观测层的 token 统计**永远是 0**。

修复两点：解析顺序改成先处理 `usage` 再判断 `choice`；请求体加 `stream_options: { include_usage: true }`（不加这一行服务端根本不回传用量）。另外最终结果必须在**流结束后**才产出，在 `finish_reason` 处提前返回同样会丢。

### 坑 4：多 Agent 改造中，评测一次抓出三个真 bug

引入多角色后第一次跑 `multiagent` 套件，9/12。三个失败全是真问题：

**① `world.present` 初始只有 `["boss"]`，钟离根本不在场。**
所以胡桃说话时压根没有其他人跑 react。日志里只有 boss 的 react span，就是因为钟离从没被放进场景。这个 bug 靠读代码很难发现——react 代码写对了，只是永远不会被触发。

**② 系统提示里写的是角色 id 而不是名字。**
`【在场的人】除了顾客，还有：regular` ——模型看不懂 "regular" 是谁，所以玩家问"店里还有别人吗"，胡桃回答"就你一个呀，今晚整间店都归你"。
修复：加一张 id → 显示名的表，同名问题也发生在场记评审上（它把 `boss` 和"胡桃"当成两个人，报告"指派给 boss 但开口的是胡桃"这种假警报）。

**③ 旁听者把玩家的话当成了对自己说的。**
玩家向胡桃点酒，钟离作为次要角色插话，开口却是"这你得问胡桃，吧台里的事我可做不了主"——因为他的 user message 就是玩家原话，他以为在问他。
修复：旁听者拿到的是转述 `（旁边有人在说话，你听见了：「…」）`。改完之后钟离的表现变成："你这人还挺执着。我跟你讲，我这杯子都是胡桃给倒的，我可不敢伸手。你冲那边喊一声，她耳朵尖着呢。"

### 坑 5：辅助调用没被计进账

导演和场记的模型调用只记了 span，没把 `usage` 累加进 trace，导致成本被系统性低估——`npm run metrics` 里显示 "director 调用 0 次"。

修复：加 `recordAuxLLM()`，把 react / 导演 / 场记 / 记忆提炼的用量都计入总量和角色账。

### 坑 6：清掉注释后重跑，评测又翻出两个既有问题

把全项目注释删除后重跑评测，出现两条失败——**都不是删注释造成的**（注释不影响行为），而是被顺带照出来的：

**① 意图路由漏了「随便给我调一杯特别的」。**
`CUSTOM` 正则里只有"随便调"，而这句话在"随便"和"调"之间插了"给我"，匹配不上，于是只能靠模型自己决定调不调工具，时好时坏。改成 `随便.{0,4}(调|来|做|上|弄)` 这类允许插词的写法，并补了 3 条用例进离线套件。

**② 模型会主动收费。**
同样是这一轮，工具调用是 `inventDrink` **加** `takePayment`——玩家没提结账，店长自己把钱收了。prompt 里只写了"顾客要结账时调用 takePayment"，没写反面的约束。补上"顾客这一句里没提钱，就不要主动收费"后恢复正常。

> 这两条说明一件事：**评测的价值不是让分数好看，而是每次你动它，它都会把之前藏着的问题再翻出来一遍。**

### 坑 7：加客人主动搭话时，评测当场抓出一个一直存在的路由漏洞

新写的「客人参与与主动搭话」离线套件第一次跑就是 15/16，挂的是这条：

```
✗ 点名叫胡桃，期望 boss ｜ 实际 regular
```

原因是 `resolveSpeaker` 的称呼匹配里有一句 `if (c.id === DEFAULT_SPEAKER) continue;`——**它根本没检查胡桃自己的名字**。这个漏洞一直都在，只是以前兜底恰好也是胡桃，所以"胡桃，你忙吗"歪打正着地落回了正确的人手里。

加了回话窗口之后就歪不回来了：窗口插在称呼匹配和默认项之间，于是"胡桃，你忙吗"被客人接走了。修法是把东家的称呼匹配补上，位置放在客人称呼之后、回话窗口之前——**窗口可以接管没说清对象的话，但不能接管已经点了名的话。**

> 一个把正确结果"蒙对"了的分支，只要周围多插一层逻辑，就会立刻现原形。这类漏洞在没有用例的项目里根本不会有人去读。

### 坑 8：胡桃当着钟离的面说"今儿还没见着人影"

玩家问钟离"你最近怎么样"，钟离答完，胡桃跟着插了一句：

> 哟，找钟离呢？他可是我这儿的常客，不过**今儿还没见着人影**。

钟离就坐在她店里，而且刚刚才说完话。这不是人设问题——翻 trace 一眼就看清楚了：

```
react boss phase=parallel speak=true urgency=0.4
  angle = 哟，找钟离呢？他可是我这儿的常客，不过今儿还没见着人影。
```

**出问题的不是台词，是那句 angle。** 胡桃的 `act` 里明明写着`【在场的人】除了顾客，还有：钟离`，但她这一拍不是主角，是先由 react 产出一个"我想说什么"，再把这个 angle 当成这一拍的目标交给 `act` 去演。而 react 的 prompt 里**只有最近几条事件，没有在场名单**——旁听者判断"我该不该插话"的时候，根本不知道屋里坐着谁，于是它按最常见的情形顺手编了句"人还没来"。

三处一起修：

1. react 的 prompt 里加上在场名单，并明说"他们就在场，别把人说成不在、没来或者没见着人影"
2. `act` 区分"导演拍的目标"和"react 给的话头"——后者只是一句意思，标注成`【你想接的话头】`，并补一句"如果它跟你知道的事实冲突，按事实来"
3. 场记的判据里加上"把在场的人说成不在场也算出戏"，这样同类问题下次会自己冒进 trace

修完再跑同一条输入，angle 变成了：

```
react boss phase=parallel  speak=false urgency=0.2  angle = 钟离在跟人说话，我先擦杯子听着就好
react boss phase=followup  speak=true  urgency=0.4  angle = 笑着接一句，调侃钟离哪里算老，明明每天都来店里坐镇
```

> **旁听者拿到的世界状态，和主角拿到的不是同一份**——主角的 prompt 里有在场名单，旁听者的没有。多角色系统里最容易漏的就是这种"某个角色的某一层视图少了字段"，它不会报错，只会让角色说出跟世界矛盾的话。

### 坑 9：记忆越丰富，胡桃越爱"顺手给你调一杯"

跑了几轮评测再回头跑在线套件，`e2e` 里两条寒暄用例开始挂：

```
✗ 你好呀          期望 不调用任何工具      实际 makeDrink
✗ 你们库存还有多少  期望 checkStock        实际 checkStock, makeDrink
```

翻一眼她当时的 prompt 就明白了——这位顾客的画像已经攒成：

```
关于这位顾客，你记得：顾客的名字是「sun」。顾客最喜欢的饮品是「大都会」。今天已经为这位顾客招待过 375 次。
```

人设里写着"只要顾客说出想要某款酒…【立刻】调用 makeDrink"，画像又告诉他"这人最爱大都会、来过 375 次"。于是"你好呀"也能触发一次调酒；问库存更直接：**查完库存顺手做了一杯。**

这跟坑 6 里的"主动收费"是同一类错误：**prompt 只写了正面指令，没写反面约束**。修法也一样，在【用工具的铁律】里补第 7 条：

> 只有顾客这一句里真的说要喝什么，才去调酒；别的都不算——寒暄、道谢、报名字、聊天气、问库存、问价格，都不要顺手调一杯，哪怕你记得他平时爱喝什么、哪怕他已经是熟客。

第一版把括号写成了封闭列表（"只是寒暄、道谢、报名字、聊天气"），结果"问库存"被漏在外面，`checkStock, makeDrink` 照旧——**枚举式规则会漏，判断式规则才收得住**。

这条也进了离线套件（`no_proactive_drink`，期望值里带着"画像很熟"这个前提），谁把规则删掉都会立刻挂。

> **记忆不是只有好处。** 上下文里每多一条"关于这个人的事实"，模型就多一分自作主张的底气——RAG 做得越认真，越需要反面约束来配平。

### 坑 10：一次专门找 bug 的复查，又翻出九个

前面九条都是评测或实跑撞出来的。这一轮反过来做：不写新功能，**带着"这里还藏着什么"把代码重读一遍，再起一个真服务逐条走**，一次性翻出九个。其中三个会被玩家直接摸到。

**① 全局键盘监听把输入框的按键吃掉了。**

```js
document.addEventListener("keydown", (e) => {
  const k = e.key.toLowerCase();
  keys[k] = true;
  if (MOVE_KEYS.includes(k)) e.preventDefault();   // ← 没判断焦点在哪
  if (k === "e" && !e.repeat) toggleSit();
});
```

`MOVE_KEYS` 里有 `w/a/s/d`，而 keydown 的默认动作就是"把字符打进输入框"。于是聊天框里**打不出 w、a、s、d**——按键被吞了，人物却在走。更糟的是 `e`：字母进了输入框，同时触发 `toggleSit()`，玩家站起来、输入框被 `setChatEnabled(false)` 禁用，**正在打的草稿一起没了**。

修法：焦点在 `input / textarea / select / contenteditable` 时直接 return，另加 `focusin → clearKeys()`——否则"按住方向键再点输入框"会让角色一直朝一个方向走。

> 这类 bug 的特点是**只在真人手里发生**：评测跑的是接口，而接口永远不会"正在打字"。

**② 输出守卫替换掉的台词，没有回写会话历史。**

`act()` 在返回前就把回复推进了历史，而 `guardAndReport()` 是在 `act()` 返回**之后**才替换台词的：

```js
history.push({ role: "assistant", content: reply });          // character.js：守卫前的原文
...
const primaryGuard = await guardAndReport({ ..., reply });    // scene.js：之后才替换
```

后果不是"少记一句"，而是**安全层会自我强化地失效**：玩家看到的是改写后的角色内台词，`sessions.json` 里存的是被拦下的原文，下一轮 `msgs = [system, ...history, user]` 又把这段原文当成"角色自己说过的话"发回给模型——守卫越拦，历史越脏。用探针强制守卫生效跑一轮，落盘的是：

```
[assistant] 哎呀，你来得正好——我今天心情好得不行，柜台都快被我擦亮了…   ← 玩家没看到这句
done.reply  （探针：输出守卫生效后的角色内台词）                        ← 玩家看到的是这句
```

修法：`guardAndReport()` 接收该角色的 `history`，替换后用 `rewriteLastAssistant()` 覆盖最后一条 assistant。改完再跑，落盘的就是玩家看到的那句。

**③ 心情判断写了个繁体错字——一行代码，默认体验就是错的。**

```js
`你此刻心情：${mood.name}，所以${mood.name === "平靜" || mood.name === "开心" ? "说话更轻快" : "情绪外露、措辞受影响"}`
```

`MOODS` 里是简体 **"平静"**，比较的却是繁体 **"平靜"**，这个分支永远不成立。而新玩家初始 `mood = 0` 正好就是"平静"，等于**开局就在给胡桃下反向指令**；顺带"超开心"也因为精确比较落进了错的分支。实测五档心情，修复前 `mood = 0`（默认）与 `mood ≥ 60` 两档都落到了错的一边（负数那两档本来就该走"情绪外露"，属于蒙对）。

**④ 客户端不渲染 `done.reply`。**

前端气泡文本**纯靠流式 delta 拼**，`done` 分支只处理 game/world/budget。于是只要这一拍没有任何 delta（预算耗尽、模型返回空 content 等），服务端认为"答过了"，玩家界面上**一片安静**。补一个 `fillMissingReplies()`：`done` 时对没有流式文本的角色用 `replies` 兜底建气泡。

剩下几个是同一轮的"低危但真实"：

| 问题 | 根因 | 修法 |
|---|---|---|
| `unknown` 幽灵角色 | 场景级的输入守卫 span 没带 actor，`actorStats` 却给它建了账，`totals.actors` 每次多算 1（实测一条只有胡桃开口的对话报 5 个角色，修后 4 个） | span 仍保留 `actor: null`，但只为非空 actor 建账 |
| 场记的 `hint` 是死数据 | 两处 `await reviewBeat(...)` 的返回值都没接收，而 critic 的 prompt 明确在要"下一拍该怎么纠正" | 存进 `pendingCriticNote`，注入下一拍的 `【场记对上一拍的意见】`（实测第 2 拍的 prompt 里出现了第 1 拍的 hint） |
| "骂人只记标记"其实没标记 | `guardInput` 算了 `abuse`，但全项目无人消费 | 写进 trace（`safety.input.abuse` / `totals.abuseFlags`），仍然放行不拦，观测台与 `npm run metrics` 都展示 |
| 工具参数不校验就落盘 | 参数 JSON 解析失败时 `args = {}`，`inventDrink` 照样往画像里写，私单里会出现 `🍸 undefined` | 按工具 schema 的 `required` 自动校验，缺参就回一条 tool 消息让模型补，不执行、不落盘 |
| 酒吧拿"咖啡 / 牛奶 / 糖 / 杯子"记账 | 从咖啡店 demo 带来的库存字段，`checkStock` 会把咖啡牛奶库存报给酒吧客人 | 改成 `{基酒, 配料, 装饰, 冰杯}`，用尽时的"偷偷补一份"也改回酒吧说法 |

另有三处协议与观测层面的收尾：被输入守卫拦下的那一拍现在也会推进世界时钟和"上一句说给谁"；工具轮结束、新一轮正文开始前会下发 `reset` 事件（客户端据此清掉被取代的那段文本，从根上消掉"跨轮次 delta 叠加"的隐患）；主动搭话补上了配对的 `leave`（原来只有 `approach`，`window.__tavernStaging` 会一直停在 `near: true`）。观测台那条 3 秒轮询也改成按 `size + mtime` 缓存 `traces.jsonl`，不再每次都全量解析。

> 九个里至少三个（吃键、守卫不回写、心情错字）是**读一遍就能看见的**，可它们都不在评测的覆盖面上——评测测的是"行为对不对"，测不出"输入框里能不能打字母"。**自动化只能守住你已经想到的地方，剩下的得走回去读代码、并且真的把服务跑起来走一遍。**

### 坑 11：客人点了单，酒没上

坑 10 修完，自己坐下来玩了一局，撞出这条。对话是这样的：

```
玩家：老板今晚上有什么特别推荐吗
胡桃：特别推荐嘛……看见那边慢慢抿着酒的那位没？钟离先生点的尼格罗尼……要不，咱也跟着来一杯？
玩家：钟离先生，你那杯酒怎么样
钟离：还是老样子，稳当。
玩家：那我也要这一杯          ← 明显是点单，该给胡桃
钟离：行啊，有眼光。不过这话你得跟胡桃说，我可做不了主……   ← 被常客接走了
```

**后果不是"答得不好"，是这一单彻底没了**：钟离没有调酒工具，于是 `makeDrink` 一次都没被调用，`servedToday` 不动，玩家什么都没喝到。往回查，**这一单是在两处叠加着丢的**：

**① "跟着点"这一整类说法，意图识别根本不认识。**

`detectIntent` 认的是酒名（`尼格罗尼`）和泛称（`酒` + 动词），而"**那我也要这一杯**"里既没有酒名也没有"酒"字——只有指代。同类说法还有"我也来一杯""给我也来一杯""跟他一样""再来一杯"。实测：

```
那我也要这一杯 → null      跟他一样 → null
我也来一杯    → null      再来一杯 → null
```

识别不出来，后面的"强制 `tool_choice` + 路由偏袒吧台"这两道保险就都不会触发。补了 `FOLLOW_ORDER` 规则专门收这类"跟着点"，并加了负例钉住边界（"我也想知道你们这儿的故事"不能被误判成点单）。

**② 上下文延续不检查"他办不办得了"。**

`resolveSpeaker` 里两条延续路径是不对称的——主动搭话的回话窗口有 `guestHandles()` 检查（"窗口抢不走吧台的活"，README 里一直这么写），而"上一句说给谁"的上文延续**没有**这道检查。于是同样的点单，走窗口能正确回到胡桃，走延续就落到钟离手里。

补上检查之后，两条路径的口径统一了：**延续只延续"聊"，不延续"办"**。聊天仍然接得上，吧台的活回到能做的人手里。离线套件里那条 `route_continuity_order` 的期望值也跟着从 `regular` 翻成 `boss`——**它原来把 bug 当成设计写进了断言里**，这正是"用当前输出标期望值"会踩的坑。

**③ 修①的时候，反而照出一个更早的过触发。**

加上兜底之后第一次实跑，"钟离先生，你那杯酒怎么样"竟然给客人上了一杯酒。翻出原因：

```js
const ORDER_VERB = /来|要|给我|点|喝|杯|续|上|整一/;   // ← 「杯」被当成了点单动词
if (DRINK_GENERIC.test(t) && ORDER_VERB.test(t)) → 判为点单
```

"你那杯**酒**怎么样"里有"酒"（泛称）也有"杯"（被当成动词），于是被判定成点单。这个过触发一直都在，只是以前最坏结果是钟离白答一句；有了兜底就变成**给客人上一杯没人点的酒**。修法是两条：把"杯"从 `ORDER_VERB` 里拿掉（点单得真的有动词，量词不算），再加一条 `ASKING` 拦问句和评价（怎么样 / 好喝吗 / 真好喝 / 为什么）。

> **这个顺序很说明问题**：一个错误的兜底，会把上游"一直没被看见的小错"放大成用户能看见的错。修 bug 的时候，先确认上游判据对不对，比急着加兜底重要。

**④ 顺带抓到的两件事。**

- **反思层重试会重复执行工具。** trace 里看得很清楚：`「再来一杯」 loops=3 reflection=[revise(retried)] tools=[makeDrink,makeDrink]`。判定 revise 之后带修正指令重跑是对的，但**副作用被算了两次**——那轮 `servedToday` 多记了一杯；如果重试的是 `takePayment`，就是**重复扣一次钱**。修法：同一次 `act` 内给"工具名 + 参数"做去重，重复调用直接回缓存结果、不再执行（跨轮不受影响，玩家真的再点一杯是新的 `act`）。
- **旁听者不该握吧台的工具。** 胡桃作为次要角色插话时，prompt 里那条"顾客说出想喝的酒就立刻调"会让她对着**不是跟她说的话**顺手调一杯（坑 9 的老毛病在旁听路径上的残留）。现在旁听且玩家这句不是点单/结账/查库存时，**这一轮干脆不给她工具**——模型看不到工具就不会去调。实测同一句"你那杯酒怎么样"，从"插话 + 调一杯"变成钟离一个人答。

修完照着原对话再跑一遍（真实模型、新会话）：

```
玩家：老板今晚上有什么特别推荐吗      → 胡桃（无工具调用）
玩家：钟离先生，你那杯酒怎么样        → 只有钟离，无插话、无调酒
玩家：那我也要这一杯                → 胡桃  makeDrink(尼格罗尼)   ✅ 单子落地
玩家：再来一杯                     → 胡桃  makeDrink ×1          ✅ 没重复执行
玩家：钟离，来杯尼格罗尼              → 钟离推话 + 胡桃同拍接单 makeDrink ✅
```

`servedToday` 最终正好是 3——**调出来的杯数第一次和玩家点过的杯数对上了**。

## 已知限制

诚实列出当前的短板。这些不是"以后再说"，是有明确证据的问题。

### 1. Reflection 层的判定精度只有约 50%

累计触发中否决的那几次里，只有一部分是确认的真阳性（表白、milk 参数）。

假阳性那例：用户问「你们库存还有多少」，`checkStock` 正确返回了库存，但审核员判定为"未带任何参数，无法满足查询意图"并触发重试——**但 `checkStock` 本来就不接受任何参数**。结果是多跑一轮，多花约 500ms 和一次调用的 token。

改进方向：把工具的参数 schema 一并喂给审核员；或对无参数工具直接跳过审核。

### 2. 导演和场记用的是同一个模型

`.env` 里的 `SMALL_MODEL` 目前没有实际可用的更便宜选项，所以 react / 导演 / 场记虽然 prompt 很短、输出很少，但仍然跑在主模型上。成本优化主要来自"调用更少、prompt 更短、不生成台词"，而不是"换了小模型"。

### 3. 未使用主流 Agent 框架

要求里常见的是"熟悉 LangGraph / AutoGen / CrewAI / MetaGPT"。本项目是自研编排。自研能证明理解原理，但不等价于框架使用经验。

计划：用 LangGraph 重做同一套流程，写一篇两者取舍的对比。

### 4. 技术栈是 JavaScript

如果目标岗位点名 Python，这个项目不能直接作为语言能力的证据。计划做 TypeScript 渐进迁移（不重写，增量改）。

### 5. 没有多智能体协商

目前是"导演指派 + 角色可否决"的偏单向调度，缺少真正的多轮协商（agent 之间就一个目标来回讨论直到达成一致）。相应的问题——通信收敛、死锁检测、协商成本上限——都还没做。

### 6. 客人接话只在"当拍没人插话"时补跑一次

为了让客人接得住主角刚说完的话，主角回完之后会补跑一次 react——但它只发生在**这一拍还没人拿到发言权**的时候。如果并行那一次已经判出有人要说话，就不补跑：那一拍客人回应的仍然是玩家，而不是胡桃。这是延迟和成本之间的取舍，不是做不到。

### 7. `stage` 协议已经在下发，画面上还没有人真的走过来

钟离的立绘已经进了游戏（`assets/regular_sit.png`，坐在吧台最左边喝酒，带一点小动作），但他**不会真的走到吧台边**——走路素材还没有，所以画布上的绘制代码现在还不读 `stage` 事件。

服务端这一侧是完整的：三种动作 `approach` / `join` / `leave`，加上 `near` / `anchor` / `pose` / `x` / `feetY` 五个字段，前端收进 `window.__tavernStaging`。接上走路素材时不用改协议，只要让绘制代码读这个对象。

三个动作现在是**成对**的：主动搭话必定 `approach` 之后补 `leave`，回话窗口里客人继续当主角时补 `join`，插话/接话同样是 `join` → `leave`（这一轮之前只有 `approach`，`near` 会一直停在 `true`，见[踩过的坑](#踩过的坑)第 10 条）。

### 8. 评测的在线套件样本偏小，而且断言会对"措辞"过敏

人设一致性 12 条、端到端 11 条、多 Agent 25 条。作为回归测试够用，作为统计结论偏薄。

更要命的是在线用例的**匹配器**：模型每次的说法都不一样，写死关键词就会误判。这一轮就撞到过一次——`role_boss` 问"你是谁"，模型答的是「站在这吧台后面、围裙上还沾着一点柠檬皮的人，还能是谁」：完全在角色内，但没命中原来的 `胡桃|老板娘|店主|调酒|看店|我这儿`，于是整套从 192/192 掉到 191/192。修法不是改 prompt，而是**把匹配器按语义放宽**（补上 `吧台|围裙|老板`）——用例要验的是"她有没有认领店主身份"，不是"她有没有说出那五个词"。

> 在线套件翻红时，先分清楚是**系统错了**还是**断言错了**。前者要修代码，后者要修用例，两者的处理方式正好相反。

### 9. 输出守卫是"事后替换"

守卫在流式输出**结束之后**才判定，此时玩家已经看到原文了。补发的 `guard_replaced` 事件会把气泡文本换成模型重写的角色内版本（重写失败则换成写死的兜底台词），但严格说这是补丁而非预防。

这一轮补上了它的下半段：替换后的台词会**同时回写会话历史**，所以不会再出现"玩家看到的 / 服务端记下的 / 下一轮喂回模型的"是三份不同文本的情况（见[踩过的坑](#踩过的坑)第 10 条）。但"玩家已经看见了原文"这条没变——真想预防，得把守卫挪到流式输出之前，代价是牺牲首字延迟。

### 10. 成本费率是示例值

`.env` 里的 `PRICE_INPUT_PER_M` / `PRICE_OUTPUT_PER_M` 默认值仅作示例，**实际成本请以服务商官网为准**。

### 11. 在线套件曾经不是隔离的：跑得越多，结果越飘（已修）

在线套件读写的是**同一份 `memory.json` / `vectorstore.json`**，也就是玩家真实游玩时用的那份。每一轮在线评测都会往里写记忆，于是同一个用例在不同时间点会拿到不同的上下文。

这条是实打实撞出来的：连续跑几轮 `--suite=all` 之后，端到端套件的「你好呀 → 不该调用任何工具」开始偶发失败——**期望没变、代码没变**，变的是这位顾客的画像已经攒到了 `今天已经为这位顾客招待过 375 次`、`最喜欢的饮品是大都会`，而人设里又写着"说出酒名就立刻调用工具"。于是模型对着"你好呀"也顺手调了一杯。单独重跑该套件又回到 11/11。

当时的症状在[坑 9](#坑-9记忆越丰富胡桃越爱顺手给你调一杯) 里用一条反面约束压住了，但根因没动。

**现在修了**：`eval/run.js` 在加载 agent 模块**之前**把 `TAVERN_STATE_SUFFIX` 设成 `.eval`（ESM 静态导入会提前求值，所以这一段的导入改成了动态 `await import()`），三个状态模块各自拼上这个后缀：

| 模块 | 平时 | 评测时 |
|---|---|---|
| `memory.js` | `memory.json` / `memory.regular.json` | `memory.eval.json` / `memory.regular.eval.json` |
| `vectorstore.js` | `vectorstore.json` | `vectorstore.eval.json` |
| `telemetry.js` | `traces.jsonl` | `traces.eval.jsonl` |

顺带把 `traces.jsonl` 也隔离了——原来跑一次评测会往观测数据里灌几十条 trace，观测台读的就是这份，"评测期间的数字"和"真实游玩"根本分不开。

想回到旧行为（故意拿真实画像测）：`node eval/run.js --suite=all --shared-state`；后缀也可以自定义：`--state-suffix=.run2`。评测产物 `eval/report.*` 仍然写进仓库，`*.eval.*` 那几份状态文件在 `.gitignore` 里。

### 12. 同一次全量评测里，套件之间仍然共享那份评测状态

第 11 条的隔离是"评测 vs 真实游玩"分开了，但**同一次 `--suite=all` 内部**，persona / e2e / multiagent 三个在线套件仍然共用同一份 `*.eval.*`；而且这份状态会**跨次保留**——第二次跑的时候，画像里已经攒着第一次的记忆了。这正是坑 9 那类"期望没变、结果飘了"的温床。

所以要么接受它（成绩按"跑过一次算一次"读），要么每次从干净状态起跑：

```bash
node eval/run.js --suite=all --fresh-state   # 先删掉 *.eval.* 再跑
node eval/run.js --suite=all --state-suffix=.run2   # 或者干脆换一套状态文件
```

`.eval.*` 这几个文件在 `.gitignore` 里，不会进仓库。
