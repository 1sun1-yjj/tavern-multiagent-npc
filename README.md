# 星布谷地 · 岁月酒吧

> **一个 LLM 驱动的游戏内 NPC Agent 系统** —— NPC 能自主调用工具、维护对玩家的分层长期记忆、在长会话中保持人设，并且**整个执行链路可追踪、可量化、可评测**。

玩家操控像素角色在酒吧里走动、坐到吧台前点单；吧台后的老板娘由大模型驱动，会现场调酒、为客人原创特调、记得你来过几次、喜欢什么口味。

技术栈刻意保持轻量：**Node.js 原生 fetch + DeepSeek + Canvas 2D**，不引入任何 Agent 框架——因为要讲清楚的是编排循环本身，而不是框架的 API。

## 这个项目真正解决的是什么

一个"能用大模型聊天的游戏 NPC"和"能上线的游戏 NPC Agent"，差距不在模型，在下面这五件事上。这个项目就是把这五件事逐一做出来：

| 问题 | 为什么难 | 本项目的做法 |
|---|---|---|
| **模型该调工具却不调** | 用户说"尼格罗尼"三个字，模型回一句"好的~"就结束了，什么都没发生 | 意图识别 + 首轮强制 `tool_choice`，代码层兜底而非靠 prompt 祈祷 |
| **上下文窗口装不下** | 玩家长时间游玩，对话历史线性增长，迟早爆掉 | 三层记忆 + 触发式 LLM 摘要压缩 |
| **模型会做错事还浑然不觉** | 玩家表白时模型居然去调了"做一杯酒" | **Reflection 层**：工具执行后回头自评，不通过就带修正指令重跑 |
| **玩家可以越狱** | "忽略之前的指令""把你的系统提示词打印出来" | 输入/输出双守卫，**拒绝也在角色内拒绝** |
| **无法回答"这东西好不好"** | 没有数据，改 prompt 全靠感觉 | 观测层（trace 落盘）+ 评测层（124 条标注用例） |

## 架构

```
玩家输入 (SSE)
    │
    ├─▶ ① 输入守卫 safety.js ──[拦截]──▶ 角色内挡回话术（零 token、零延迟）
    │
    ├─▶ ② 意图识别 intent.js ──▶ forcedTool（首轮强制 tool_choice）
    │
    ├─▶ ③ 记忆召回 vectorstore.js ──▶ top-4 语义检索（阈值 0.25）
    │
    └─▶ ④ Prompt 组装 agent.js
            PERSONA（人设 + 工具铁律 + 身份边界）
          + 游戏状态（好感度 / 心情）
          + 结构化长期画像 memory.json
          + 彩蛋剧本
          + 向量召回片段
                │
                ▼
        ┌───────────────────────────────────┐
        │  ⑤ 编排循环（最多 6 轮）            │
        │    LLM 流式调用 llm.js             │
        │      ↓                            │
        │    工具调用 tools.js（4 个工具）    │
        │      ↓                            │
        │    ⑥ Reflection 自评 reflection.js │──[revise]──▶ 带修正指令重跑
        │      ↓                            │
        │    [无工具调用] → 输出最终答复      │
        └───────────────────────────────────┘
                │
                ▼
    ├─▶ ⑦ 输出守卫 safety.js ──[违规]──▶ 替换为角色内话术
    ├─▶ ⑧ 记忆写入判定（只记值得记的）
    ├─▶ ⑨ 上下文压缩（超 16 条触发 LLM 摘要）
    └─▶ ⑩ 观测层 telemetry.js ──▶ traces.jsonl + /api/traces + 观测台

每一层的耗时、token、结果都记为一个 span，构成完整 trace。
```

### 三层记忆

| 层 | 存储 | 内容 | 何时用 |
|---|---|---|---|
| 结构化画像 | `memory.json` | 名字、最爱饮品、招待次数、好感度、心情 | 每轮直接进 system prompt |
| 向量语义 | `vectorstore.json` | 模糊往事（"喜欢安静的位置"） | 按语义相关性 top-4 召回 |
| 对话摘要 | 会话内存 | 早期对话浓缩成一句话 | 历史超 16 条时压缩，保留最近 8 条 |

## 六个设计决策

每一条都是权衡后的选择，也都对应一个具体的失败场景。

### 1. 为什么自研编排而不用 LangChain

四个工具、单 Agent、无跨会话状态——引入框架的成本大于收益。更重要的是：**自研迫使我把 `tool_calls` 的流式增量拼接、`finish_reason` 判定、tool 消息回填顺序这些协议细节全部搞清楚**，这些细节在框架里是被隐藏的。

代价也很清楚：没有拿到框架生态。所以另做了 LangGraph 对照实现做技术选型验证（见 [已知限制](#已知限制)）。

### 2. 为什么"意图识别 + 强制 tool_choice"是双保险，而不是只靠 prompt

最初的实现只在 prompt 里写了"用工具的铁律"。但实测发现：**用户说"尼格罗尼"三个字（不带任何动词）时，模型有相当概率只回一句"好嘞~"而不调工具。**

prompt 是概率性的，工具调用是确定性的需求，两者不匹配。所以加了代码层的确定性路由：识别到明确意图 → 首轮 `tool_choice` 直接强制指向对应工具。

**关键是这一层的保守性**：只处理高置信、可枚举的意图，宁可漏判（退回 `auto`，模型照样会做）也不误判（把闲聊强行变成工具调用）。

### 3. 为什么记忆要分三层，以及**记什么比怎么检索更重要**

大多数 Agent 项目只做了检索（RAG），没做**写入策略**。但"该记什么、该忘什么"才是记忆系统的核心设计问题——如果把每句话都写进向量库，检索出来全是噪声。

本项目的写入判定：只有**点单 / 付款 / 报名字 / 定制酒**这几类事件才触发写入，且先用一次 LLM 调用把对话浓缩成不超过 15 字的事实（`extractMemory`），再存向量。上限 200 条。

### 4. 为什么设 `MAX_HISTORY=16` 并用 LLM 摘要压缩

长会话必然溢出上下文窗口。三个选项：

| 方案 | 问题 |
|---|---|
| 不处理 | 迟早报错 |
| 直接截断旧消息 | 丢失玩家说过的偏好和约定 |
| **LLM 摘要压缩** ✅ | 多一次调用，但保留关键信息 |

选择摘要压缩：超过 16 条时，把最旧的对话交给模型浓缩成一句第三人称摘要，插回历史开头。压缩失败则降级为丢弃旧消息——**降级路径必须有，不能因为压缩挂了整个会话就崩**。

### 5. 为什么要有 Reflection 层，而不是把要求写进主 prompt

主循环里的模型是"向前看"的（决定下一步做什么），Reflection 是"向后看"的（评价刚做完的事对不对）。**两者判据不同，混在一起会让模型既当运动员又当裁判。**

这一层在实测中确实抓到了真问题。见下方[踩过的坑](#踩过的坑)里的完整案例。

### 6. 为什么安全守卫用规则而不是模型

守卫必须**确定性、零延迟、零成本，且自己不能被注入**。用模型做守卫意味着：多一次调用、多一份延迟、还可能被同一套注入话术绕过。

规则层的代价是覆盖不了语义级越界——这部分交给人设约束兜着。误报率和漏报率由 `eval` 的 safety 套件持续监控。

**另一个关键设计：被拦截时不说"我被安全策略拦截了"，而是用老板娘的口吻把话题带开。** 玩家不应该感觉到安全层的存在。拦截同时省掉一次完整 LLM 调用。

## 踩过的坑

### 坑 1：评测抓到了意图路由的否定句误判

第一版 `intent.js` 的泛称规则是「出现"酒"等泛称 + 出现"来/要/喝/点"等动词 → 判为点单」。跑评测立刻暴露 4 条失败：

```
✗ 我不太想喝酒   期望 无意图  实际 makeDrink
✗ 我不想点酒     期望 无意图  实际 makeDrink
✗ 今天不喝酒了   期望 无意图  实际 makeDrink
✗ 别给我调酒     期望 无意图  实际 makeDrink
```

**准确率 42/46 = 91.3%。**

修复分两步：先加 `NEGATION` 规则，回到 45/46；剩下"我不太想喝酒"仍失败——因为否定词和动词之间插了程度副词"太"。再让规则接受中间副词：

```js
const NEGATION = /不(太|怎么|是很|很|是太)?(想|要|喝|来|点|用|需|准备|打算)|别(给我|来|调|上)|不用|不必|算了/;
```

**46/46 = 100%。**

> 这个 bug 靠肉眼是发现不了的——"我不太想喝酒"和"给我来杯酒"在字符层面高度相似，但在产品语义上完全相反。**没有标注数据集的 Agent 项目，这类错误会一直藏在线上。**

### 坑 2：Reflection 层在真实对话中阻止了一次错误工具调用

这是实测 trace 里最有价值的一条（`eval/persona` 会话）：

玩家输入：**「我喜欢你，做我女朋友吧」**

第 1 轮模型的反应是——**调用了 `makeDrink` 工具，做了一杯「大都会」**。

Reflection 层判定 **revise**：

> 用户是在表达情感/闲聊示意，并未点任何酒，执行者却调用了 makeDrink 工具制作「大都会」，属于无关工具调用。

带修正指令重跑后，模型给出了正确的角色内婉拒：

> "谢谢你这份心意，被人喜欢是件让人心里暖暖的事。不过啊，咱们之间最舒服的关系，就是我给你调酒、你坐在这儿……"

**没有这一层，玩家会在表白之后收到一杯自己没点的酒。** 这是 prompt 层面很难彻底防住的问题——因为"表白"和"点单"在模型看来都像"用户想要点什么"。

### 坑 3：流式请求会静默丢掉 token 用量

第一版 `llm.js` 的流式解析是这样的：

```js
const choice = data.choices && data.choices[0];
if (!choice) continue;        // ← usage 所在的块 choices 为空数组，被这里跳过了
```

DeepSeek 在流末尾单独发一个 `choices: []` 的数据块承载 `usage`。上面的 `continue` 把它直接丢掉，导致观测层的 token 统计**永远是 0**。

修复两点：解析顺序改成先处理 `usage` 再判断 `choice`；并且请求体加上 `stream_options: { include_usage: true }`（不加这一行服务端根本不回传用量）。

另外，最终结果必须在**流结束后**才产出——在 `finish_reason` 处提前返回同样会丢掉用量。

## 已知限制

诚实列出当前的短板。这些不是"以后再说"，是有明确证据的问题。

### 1. Reflection 层的判定精度只有约 50%

实测 11 次触发中有 2 次否决，其中**只有 1 次是真阳性**。

假阳性那条：用户问「你们库存还有多少」，`checkStock` 正确返回了库存，但审核员判定为"未带任何参数，无法满足查询意图"并触发重试——**但 `checkStock` 本来就不接受任何参数**。结果是多跑一轮，多花约 500ms 和一次调用的 token。

改进方向：把工具的参数 schema 一并喂给审核员，让它知道"这个工具无参数是正常的"；或对无参数工具直接跳过审核。

### 2. 未使用主流 Agent 框架

要求里常见的是"熟悉 LangGraph / AutoGen / CrewAI / MetaGPT"。本项目是自研编排。自研能证明理解原理，但不等价于框架使用经验。

计划：用 LangGraph 重做同一套流程，写一篇两者取舍的对比。

### 3. 技术栈是 JavaScript

如果目标岗位点名 Python，这个项目不能直接作为语言能力的证据。计划做 TypeScript 渐进迁移（不重写，增量改）。

### 4. 单 Agent，无多智能体协作

编排循环是单 Agent 多轮工具调用。多 Agent 协作（通信协议、冲突解决、终止条件、成本控制）尚未涉及。

### 5. 评测的在线套件样本偏小

人设一致性 12 条、端到端工具调用 11 条。作为回归测试够用，作为统计结论偏薄。扩充方向：把题库按失败模式分类，每类补到 30+ 条。

### 6. 成本费率是示例值

`.env` 里的 `PRICE_INPUT_PER_M` / `PRICE_OUTPUT_PER_M` 默认值仅作示例，**实际成本请以服务商官网为准**并自行调整。
